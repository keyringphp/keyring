# Release Notes

## Unreleased

### Single Sign-On

- A `SingleSignOn` factor signs users in with identity providers, with no other package: Google, Microsoft (any tenant, organisations, personal accounts, or one tenant), GitHub, and any OpenID Connect provider through discovery. Configure them under the new `sso` config section, and register drivers of your own with `Keyring::sso()->extend()`. See [Single Sign-On](docs/sso.md), and [More Identity Providers](docs/sso-providers.md) for the config of eight more OpenID Connect providers and drivers for Discord, Bitbucket, Facebook, and LinkedIn.
- `GET /auth/{provider}/redirect` (`keyring.sso.redirect`) sends a guest to the provider, and `GET /auth/{provider}/callback` (`keyring.sso.callback`) is the one URL each provider sends users back to, for signing in, for linking and for confirming. They're only registered when `sso.providers` lists a provider, and answer `404` until the factor is registered. The callback only finishes Keyring's own sign ins, links and confirms, and a guest's draws on the `keyring-login-options` rate limiter. The `login` page gets a `providers` prop with each provider's `name`, `label` and `url`. A provider that can't be built, such as one missing its `client_id`, one whose name holds more than letters, digits, `-` and `_`, or one whose `scopes`, `parameters` or `token_endpoint_auth_method` isn't something it can take, is reported and left off the page rather than failing it. A callback whose request has expired, while someone is signed in, fails straight away rather than as a link, without asking for a fresh verification or logging a refused link: a confirm goes back to the confirm page with `expired`, even once the confirm itself has run out, and a link back to the page it was started from with `enrollment_expired`. One whose request this browser doesn't have at all goes back to the confirm page with `expired` while a confirm is in progress, and `home` otherwise.
- A sign in with a provider goes through the same pipeline as the login form, so rate limits, the policy and risk apply, and a user with a second factor is still asked for it. It counts as a knowledge factor, like the password, and is never offered on the challenge page.
- A sign in, or a new link, with a provider whose `freshness` is `reauthenticate` counts toward `keyring.fresh` from its `auth_time`, which Keyring asks for where the provider takes the `claims` parameter, so one the provider let straight through on an old session isn't a fresh verification, and one without `auth_time` never is. With `never` it never counts. Its session and assurance level still start when the user came back either way. Only a provider opted into `round_trip` counts from when the user came back, whatever `auth_time` it sends. `Verification` has a new `authenticatedAt`, with `Verification::UNKNOWN` for a provider that didn't say when, `provedAt()` gives the earlier of the two, and `SessionAssurance::provedSince()` is what freshness reads. `SignIn::enrolled()` takes the `Verification` adding a method proved.
- A link confirms a step-up: the confirm page offers it, with the new `GET /confirm/sso/redirect` (`keyring.sso.confirm`) in its `challenge` as `url`, which sends the user back to the provider with the link's address as `login_hint`. A provider whose `freshness` is `reauthenticate` is sent `max_age=0`, with `prompt=login` where it takes it (not at Google, and in place of `max_age` at Microsoft), and the confirm needs an `auth_time` no earlier than when the user was sent there, give or take a minute. One opted into `round_trip` gets a plain round trip, which counts as much as signing in with it again does. One that's `never` gets a plain round trip too, which counts toward the session's level, as signing in again would, and never toward `keyring.fresh`, so it's only offered toward a level, such as after AAL2 lapses. `keyring.fresh` only asks for what can be proved recently, so a user with a `never` link and a second factor, and no password, confirms with the second factor alone, and one who can't confirm at all gets `enroll-first` straight away. The round trip never sets Laravel's `auth.password_confirmed_at`, and a visit to `/confirm` of the user's own, where `password.confirm` sends them, only offers what can be proved recently, so a user still signed in to GitHub doesn't pass `password.confirm` without typing anything. `StepUp::unlessMet()` and `meets()` with both a level and a moment ask for them in turn, the level first, when the account can't freshly prove the level, so a user with a `never` link and an authenticator app, and no password, isn't sent to enroll. A recovery code isn't offered on a fresh verification that only the link could finish beside it. The callback only confirms the same account, for the user and the confirm that started it, and goes through the confirm page's pipeline, so rate limits and events apply as they do there. `IdentityProvider` has a new `supportsReauthentication()`, saying whether the provider can be asked, and `freshness()`, `Keyring::sso()->start()` takes a `maxAge` and a `loginHint`, `AuthorizationRequest` keeps when it was made (`createdAt`), and `complete()` refuses an identity without a recent enough `authTime` with the new `SsoFailure::StaleAuthentication`.
- A provider's `freshness` option, a `Keyring\Enums\SsoFreshness`, says how much its sign ins and confirms count toward `keyring.fresh`: `reauthenticate`, `round_trip`, or `never` (or `false`). The defaults are the most secure each driver can give: `reauthenticate` for `oidc`, which asks for `auth_time` with the `claims` parameter where discovery says it's taken, and for `microsoft`, which needs the `auth_time` optional claim added to the app registration (without it no sign in is fresh, and a confirm fails with a reported `StaleAuthentication` that says what to add), and `never` for `google`, `github`, and drivers built on `OAuth2Provider`. `round_trip` is only ever an opt-in. `reauthenticate` throws an `InvalidArgumentException` for a provider that can't be asked, such as GitHub. When a link's provider and the one a sign in came through differ, the stricter counts, so renaming or removing a provider never makes a sign in count for more. A link only takes the name of the provider a sign in or a new link of the same account came through once its own is no longer configured, so the stricter keeps counting however many sign ins come through the other. The config's `freshness` wins over a driver's own `freshness()`, for drivers of your own too, and `Keyring::sso()->freshness()` gives the value that counts. A user whose only way in is a `never` link can't make protected changes, and gets out with a password reset. See [Freshness](docs/sso.md#freshness).
- Accounts at providers are matched on their issuer and subject, never on the email address. Nobody is signed up or linked by their address, and an account nobody linked gets the same error as a wrong password. Users link accounts from your settings page with `POST /user/authenticators/sso`, which needs a fresh verification and a verified address, and unlink them like any other authenticator. A link comes with no recovery codes and is never the default.
- Every request carries PKCE (S256), a `state` kept in the browser's session and used once, and for OpenID Connect a `nonce`. ID tokens are checked for their signature against the provider's published keys, issuer, audience, times and nonce, and a callback naming another issuer (RFC 9207) is refused. Microsoft addresses count as unverified unless the tenant vouches for the domain with `xms_edov`, and a GitHub address only counts as verified when it's the primary one GitHub has verified.
- A completed password reset unlinks every provider linked to the account, before it signs every session out and again after, and an undone email change unlinks the ones linked since. The `sso` factor key is reserved for the factor.
- A user who says no at the provider is sent back with the new `sso-cancelled` status. Failed sign ins are logged as `factor_failed`, and refused links as `enrollment_refused`. Every `SsoFailed` Keyring catches is reported to the exception handler, apart from a user saying no and a spent or unknown state (`SsoFailed::expected()`).
- Discovery documents and key sets are only cached once they've been checked, and a provider's RSA keys have a 2048-bit floor of their own (`SignedToken::SHORTEST_RSA_KEY`), apart from passkeys' `minimum_rsa_bits`. An issuer elsewhere can't name plain HTTP endpoints, nor a token endpoint or key set on a private or local address other than on its own host and port, unless the new `private_endpoints` option says it may. Microsoft's `organizations` tenant refuses personal accounts.
- `token_endpoint_auth_method` takes `none` for a public client, and a driver built on `OAuth2Provider` adds values of its own with `allowedAuthMethods()`. `scopes` leaves out a `null` or empty string, so an `env()` can turn one off.
- `FactorFailed` has `firstFactor()` and `afterFirstFactor()`, and `afterPassword()` is now only `true` after the password. A second factor failing after a sign in with a provider is still logged as `second_factor_failed`, and its email names the link that was used instead of saying the password was entered.
- Laravel's `Failed` event only takes the username from the request for a factor that asks for one, so an identity provider's callback can't put one there with its query string.
- `Keyring\Testing\FakeIdentityProvider` stands in for a provider in tests, with really signed ID tokens carrying an `auth_time` (leave it out with `withClaims(['auth_time' => null])`), and the authenticator factory has an `sso()` state. It signs the user in again when asked to with `prompt=login` or `max_age`, `signedInAt()` gives them an older session there, and `ignoringReauthentication()` keeps using it when asked not to. The fake Google only sends `auth_time` when the `claims` parameter asks for it, and the fake Microsoft only after `withAuthTimeClaim()`, as Microsoft only does with its optional claim. `withKeyIssuer()` changes the `issuer` its keys name, which the fake Microsoft's do as Microsoft's do. Endpoints are refused when their host resolves inside the network, so host names are looked up with `Keyring\Sso\HostResolver`, which the fake swaps for `HostResolver::fake()`. `SingleSignOn::credentialId($issuer, $subject)` gives the credential ID a link is stored with, for links made by your own code.
- A sign in, confirm, or new link with a provider keeps the provider's `amr` and `acr` on the session's `Verification`, as `providerAmr` and `providerAcr`, for an app that reports how the user signed in. They're the provider's claim and count toward nothing, not the level, the categories or phishing resistance. At most 10 `amr` values of a plain form are kept, and an `acr` up to 255 printable characters, so a provider can't fill the session. See [Second Factors and Policies](docs/sso.md#second-factors-and-policies).
- A `ProviderIdentityAccepted` event, with the `user`, the link, the provider's `Identity` and the `purpose` (`login`, `confirm` or `link`), fires when a provider's account is accepted as the user's link. A sign in only fires it once the account matched a link, and before any second factor. Queued, its identity's request has no state, nonce or code verifier, and its claims have no `nonce`, `at_hash` or `c_hash`. See [Hearing About Accepted Identities](docs/sso.md#hearing-about-accepted-identities).
- The Socialite recipe is gone. [Migrating From the Socialite Recipe](docs/sso.md#migrating-from-the-socialite-recipe) moves its `github_id` links into the factor.
- A factor of your own that can only start a sign in (`answersChallenges()` returns `false`) no longer gets recovery codes with its first authenticator, isn't made the default, can't be made it with `PATCH /user/authenticators/{authenticator}`, and doesn't count as a second factor that recovery codes are kept for.

### Impersonation

- `Features::impersonation()` lets someone sign in as another user and come back, in place of packages such as `lab404/laravel-impersonate`. Nobody may until `Keyring::allowImpersonationWhen()` says who may impersonate whom, and Keyring always refuses impersonating yourself, an account its guard wouldn't load, a user who may not sign in, and starting a second one while impersonating. `Keyring::allowsImpersonation()` asks for a button that only shows when it would work. See [Impersonation](docs/impersonation.md).
- `POST /impersonate/{user}` (`keyring.impersonation.store`) starts, behind the new `impersonation.middleware`, two factors proved in the last 15 minutes by default, and `POST` or `DELETE /impersonate` (`keyring.impersonation.destroy`) stops, answering a stop with nobody being impersonated, a second one from another tab say, as back already: a `409` `not-impersonating` for JSON clients, which the browser package's `stopImpersonating()` resolves with, and `impersonation.return_url` for a page. Both answer with a status response (`impersonation-started`, `impersonation-ended`) that sends `Clear-Site-Data`, to `impersonation.redirect_url` and `impersonation.return_url`, and have an Inertia visit load that page in full. `Keyring::impersonate()` and `Keyring::stopImpersonating()` do the same from a controller of your own, and a refusal throws the new `ImpersonationRefused`, a `403`, answered to JSON clients with the `impersonation-refused` status whatever the reason, whose `reason` is the new `Keyring\Enums\ImpersonationRefusal`: `disabled`, `no_callback` (the feature is on but `Keyring::allowImpersonationWhen()` was never called), both of which also write a warning to the app's log naming what's missing, `self`, `not_allowed`, `impersonating` or `unregistered`. `Keyring::impersonationRefusal()` says which, ahead of starting.
- The impersonated session is a registered session of its own, on a new session ID, that names the impersonator and their parked session: nothing proved, never remembered, on no device, and ended by itself after `impersonation.lifetime` (an hour), which is checked when the app boots with the feature on. The user's own `Login` and `Authenticated` don't fire, no risk signals are assessed on it, `InactiveAccount` doesn't count it as the user using their account, and nothing the impersonator proved carries over. Who may impersonate whom is asked again on every request, and a callback that throws there is reported and ends the impersonation, where it's thrown on before starting. Going back takes the impersonator's own session still being good, the impersonator still allowed to sign in, not held for a new password and on the password they had when it started (its hash then, compared in the form Laravel's `auth.session` compares, whether or not that runs, so any change to it meanwhile, a rehash, a password set or removed, or Keyring's own change with `sign_out_others` off included, signs the browser out rather than going back), and the browser's session still being the impersonation it started. It restores that session, kept from lapsing while the impersonator was busy though a gap between requests past a level's idle limit still lapses it, and Laravel's `auth.session` password hash, but at AAL1 at most and with nothing counting as fresh, since a page of the user's could have sent the stop: only as much of what was proved as stays short of AAL2 is kept, the password ahead of anything the impersonator has, so `keyring:aal2` and `keyring:aal3` ask for the second factor again (the password still counts), and `keyring.fresh` asks again. Its new record has the level it came back at. Under `sessions.end_on_lapse`, where a session doesn't outlive the level it signed in at, an impersonator whose session signed in above AAL1 is signed out instead, with `impersonator_session_ended`, as coming back at AAL1 would be that level running out. Otherwise the browser is signed out, as it is when the impersonator's own session ends meanwhile, or the user can no longer be loaded. An impersonated session isn't one of the user's under `sessions.max`. Their "remember me" cookies are left alone while it lasts. Going back moves their session to a new record on every session driver, as a step-up does, so a copy of the session from while impersonating leads nowhere, and Keyring's "remember me" cookie moves with it. Only one request ends an impersonation, however many of the browser's find it over at once: the first to claim its end, in the rate limiter's cache store, whatever ended its record meanwhile. A store that fails lets the request end it anyway, and is reported. The rest are answered as signed out with `lost`, and log, announce, revoke and move nothing. `Sessions::reregister()` returns whether the session moved. Signing out while impersonating leaves the user's "remember me" token alone, also when the session registry fails, which changes the impersonator's instead when their parked session couldn't be ended. Starting and going back forget Laravel's `url.intended`, so a page of the user's can't choose where the impersonator's next confirm or sign in goes.
- While impersonating, Keyring refuses password and email changes, authenticator changes, ending sessions and devices, confirming a step-up, verifying the email address and sending the verification link again, and starting another impersonation with a `403` and the `impersonating` status. Step-up middleware answers the same rather than sending the browser to confirm. The new `keyring.not-impersonating` middleware refuses routes of your own. `keyring.enrolled` and a password hold let an impersonating browser through.
- `Keyring::impersonating()`, `Keyring::impersonator()`, and `Keyring::impersonation()`, what a banner needs, read from the session. Its `expiresAt` is when the impersonation really ends, capped by `sessions.absolute` as its record is. The browser package has `impersonate()`, `stopImpersonating()`, `routes.impersonate()`, `routes.stopImpersonating()`, and the `Impersonation` type.
- The sessions list marks an impersonated session as `impersonated`, with the impersonator as `impersonator`, `{"name": "..."}` with no ID, for the user to end, unless `impersonation.show_in_sessions` is `false`. It shows no `name`, `ip` or `device` for it, as they'd be the impersonator's, and its record doesn't keep the impersonator's IP address or browser. Nor does the security log on the user's account: `impersonation_started`, `impersonation_ended`, and any other entry written on the user's account while impersonating have no `ip` or `user_agent`, while the impersonator's entries keep them.
- `impersonation_started` and `impersonation_ended` are left out of `Keyring::activity()`, and are in `Keyring::unlistedActivityTypes()`, when `impersonation.show_in_activity` is `false`. They're still logged. Listing them in `security_log.unlisted` doesn't hide them, as with Keyring's other types.
- `impersonation_started` and `impersonation_ended` are logged on both accounts, with why it ended, and the `ImpersonationStarted` and `ImpersonationEnded` events fire, each with the impersonated session's `handle`, which is among the `handles` its record's `RegisteredSessionEnded` carries when the browser never comes back. The start is logged before the browser changes hands and before `ImpersonationStarted`, and a start that can't be logged is refused. The end is logged, and `ImpersonationEnded` fires once, even when signing out or going back fails after the sessions were ended, and when signing out can't end the impersonator's parked session. Going back that fails, handing the browser back or moving the impersonator's session to a new record, ends the impersonator's session and signs the browser out, and so does a sign in that can't end an impersonation the session still holds. A start that can't be logged takes the user's record back without a `RegisteredSessionEnded`, and the sweep doesn't announce it later. So does one that's logged but can't hand the browser over, an app's `Authenticated` listener that throws say, which leaves the impersonator's session as it was and logs the end with the new `failed` reason, without either event. A refused start is logged as `impersonation_refused` on the impersonator's account, with the reason, one of `ImpersonationRefusal`'s or `not_found` for an ID nobody has, or one the database won't look up (an error in SQLSTATE class `22`, where any other is thrown on), and the ID asked for. A browser signed out because an impersonation couldn't go back gets `SignedOutResponse` with the `impersonator_session_ended` or `lost` reason, or, when the session middleware finds it on a route in `sessions.continue_as_guest`, is asked for the page again as a guest. Records an impersonation ends are announced with the new `SessionEndReason::ImpersonationEnded`.
- `keyring:install --feature` takes `impersonation`, and its help lists it.
- A new migration adds `impersonator_id`, `impersonator_type`, and `impersonator_session` to `keyring_sessions`. Only an impersonated session writes them. On the `database` driver, starting without them throws a `LogicException` that names them and says to run `keyring:install` and `migrate`, asking the database once and then the cache for a few minutes.

### Headless Frontends

- A JSON request for one of Keyring's pages, one that isn't an Inertia visit, gets the page's name and props as `{"page": "...", "props": {...}}`, for a frontend Laravel doesn't serve, such as a Nuxt app. Laravel counts an XHR that accepts anything as a JSON request too, so a Blade page that loads one with jQuery now gets JSON (see the [upgrade guide](UPGRADE.md)). It's sent with the same headers as the page, `Referrer-Policy: no-referrer` and `Cache-Control: no-store` on the pages emailed links open included, never throws `MissingPage`, and isn't noted as the page to go back to. A page you render with a closure through `Keyring::page` still decides what it answers.
- A `pages` config option. Set it to `false` when every page is in such a frontend, and a page request that isn't JSON gets a `404`.
- JSON answers that send the browser to one of Keyring's pages name it as `page`: `challenge` and `confirm` on the challenge response, `confirm` on the `423` for step-up, `login` on the `401` for a session Keyring ended, which also gains a `redirect` to the login page, and the page a status response's `redirect` goes to, such as `login` after a password reset.
- A JSON request to a sign in or step-up that ran out or used up its code guesses gets a `422` with the reason on the field, as a page visit's redirect flashes it, and the page to start again on as `page` and `redirect`. It used to be redirected, and a `fetch()` that followed the redirect lost the error.
- Verifying an email address answers JSON requests with an `email-verified` status, `justNow` and the `redirect`, where it always redirected.
- A guide to [headless frontends](docs/headless.md): Sanctum, CORS, cookies, CSRF, passkeys, emailed links that open the frontend, mapping pages and answers to its routes, and rendering on the server with Nuxt.

### Browser Package

- `@keyringjs/keyring` 0.2.0. `configureRequests()`, for a frontend Laravel doesn't serve, such as a Nuxt application on `app.example.com` calling Laravel on `api.example.com`. `baseUrl` sends every path `json()` is given there, Keyring's routes included, after the route prefix. Requests to it then send cookies (`credentials: 'include'`) unless told otherwise with `credentials`, and everything stays `same-origin` without a `baseUrl`, so Inertia applications see no change. `csrfCookie` names a URL such as Sanctum's `/sanctum/csrf-cookie` to fetch before a request that needs the `XSRF-TOKEN` cookie when it isn't there, once for requests made together, and throws when the cookie arrives but the page can't read it. `fetch` replaces the global `fetch`. An option it doesn't have, such as `baseURL`, throws. See [Frontends on Another Origin](docs/frontend.md#frontends-on-another-origin).
- `json()` no longer throws when rendering on the server, where there's no `document`. It sends no XSRF token there.
- `signInWithProvider()`, `linkProvider()` and `confirmWithProvider()` send the browser to an identity provider to sign in, to link an account, or to confirm a step-up, `routes.ssoRedirect()`, `routes.ssoCallback()` and `routes.ssoConfirm()` give their paths, and the `LoginProps`, `IdentityProvider`, `SsoAuthenticator`, `SsoEnrollment` and `SsoChallenge` types describe what Keyring sends. See [Signing In With an Identity Provider](docs/frontend.md#signing-in-with-an-identity-provider).
- `passkeyCredential()` and `isAbort()` are in the main entry point too, so a frontend without Inertia can sign in with a passkey without installing `@inertiajs/core`. The `inertia`, `vue`, and `react` entry points still export them.

### Sessions and Devices

- A sign-out your app does itself also ends the registered session when the app empties the session first, as in `$request->session()->invalidate()` or `flush()` followed by `Auth::logout()` or `Auth::logoutCurrentDevice()`. Before, the record stayed good until it timed out and no `RegisteredSessionEnded` went out. On the `cookie` session driver a copy of the session stayed signed in, and after `logoutCurrentDevice()` so did a kept copy of the "remember me" cookies. It works on any route Keyring's session middleware runs on.
- With `sessions.max`, a sign in whose limit fails to end a session, on the `cache` driver or a registry on a `sessions.connection` of its own, revokes its new record again without a `RegisteredSessionEnded`, as before, and now `keyring:sweep` doesn't announce it later either.

### Policies and Step-Up

- `Verification::provedAtIfKnown()` gives when the user proved it, or `null` when that's unknown, where `provedAt()` gives `Verification::UNKNOWN` (`0`). [Reading What Was Proved](docs/step-up.md#reading-what-was-proved) now builds `auth_time` with it.
- `continue` on the `authenticator-added` status only comes back once the account can meet what sent the user to enroll. Adding an email code on the way past `keyring.enrolled`, or an authenticator app on the way to an AAL3 page, used to hand back the page, and following it sent the user straight back to enroll. Now the page stays saved and comes back with the sign-in method that does meet it. When `keyring.enrolled` stops a route that also asks for `keyring:{level}`, the page waits for the stricter of the two. Recovery codes don't count toward it. A page saved before the upgrade, with no requirement kept beside it, comes back with the next sign-in method added, as before. It goes by what a confirm could meet (`UserKeyring::canConfirm()`), as step-up does, so a sign-in method the confirm page can't ask for doesn't count either.
- A confirm sets Laravel's `auth.password_confirmed_at` to the latest moment the user proved one of the factors it added (`Verification::provedAt()`), not to when it finished, and never moves it back. What it built on, such as the password from signing in, doesn't count.

### Security

- An authenticator is established once the account has had it for `authenticator_changes.established_after`, 7 days by default, and a set of recovery codes once that set is as old. Only established keys raise the bar. Signing in counts as a fresh verification, so a stolen copy of a session that had just signed in could add a passkey and lock the owner out: under `noDowngrade()`, or a `phishingResistant()`, `deviceBound()` or `aal3()` policy with `ifEnrolled()`, the new key made the owner's password and authenticator app stop working at once. Without those, the copy could add a key and then remove the owner's app. Either way it could replace their recovery codes, and a password reset left all of it in place. A policy with `ifEnrolled()` that asks for more factors than the owner had, such as `factors(3)`, did the same with a key of a new kind. Now a newer key signs in like any other, and counts when it's used, but only established authenticators decide what an `ifEnrolled()` policy asks for, so those policies only ask for a key, or a third factor, once the account has an established one. An account with a password and no established second factor, which needs the password to add one, is still asked for its new factor at once, unless that factor was added without the password being checked for it (before the account had one, say), and a fresh verification only asks for a key that can't leave its device when that key is established. A policy without `ifEnrolled()`, and middleware such as `keyring:aal3`, take any key that qualifies. Thanks to [@octoper](https://github.com/octoper) for suggesting this approach, after Google's.
- Adding a second factor to an account with no established one, such as a password-only account, takes the current password as `password` when the enrollment begins. A copy of a session that had just signed in could give such an account an authenticator app or passkey its owner didn't have, and the owner was then asked for it at every sign in. A wrong password counts against the password's rate limits and dispatches `FactorFailed`, and one the limits refuse is answered as at the login form, with `Lockout` and, at the cap on failures in a row, `AccountLocked`. Accounts without a password are unchanged. A first password set from a session, with no current one to type, counts as a new sign-in method: it isn't established for 7 days, freezes the account, isn't asked for by an `ifEnrolled()` policy, and isn't asked for to add a factor until then, so neither it nor a factor added with it can shut out the owner. A reset makes the password established. `AuthenticatorChanges::add()` takes `passwordConfirmed: true` for your own code, and throws `PasswordRequired` without it, `needsPassword()` says whether it's needed, and `EnrollmentRefused` can have the reason `password`.
- The password for removing the last second factor is checked under the password's own rate limits, as at a step-up, before the removal's row lock. It was only held to the `keyring` form limiter, with no count of failures in a row and no `FactorFailed`. An app that doesn't register the password factor no longer asks for one there.
- An account's sign-in methods are frozen while it has an authenticator that isn't established, or a first password set from a session in the last 7 days, and for 7 days after it removes or replaces an established one or an established set of recovery codes that had codes left. While frozen, removing, renaming or replacing an established authenticator (a factor of your own that allows one per user included), and replacing established recovery codes, are refused with a `422` on `authenticator`. The JSON says why and until when as `frozen`, and which factors could make the change now as `frozen.skip`. Removing a newer authenticator always works, and freezes nothing, so the owner can remove one someone else added. Making the first recovery codes, or replacing a set made in the last 7 days, always works too. It's checked in `AuthenticatorChanges`, under the row lock removals already take, so JSON clients and your own code get it too. `remove()`, `add()` and `update()` take `ignoreFreeze: true` for your own support tools. See [Frozen Sign-In Methods](docs/authenticators.md#frozen-sign-in-methods).
- While frozen, the owner can still make one change by proving a passkey or security key the account has had for `established_after`, and since before the session signed in. A factor of your own counts when its `phishingResistant()` says so, with its `challenge()` kept for that change. The proof goes in the change's own request, as `proof`, and is answered for that change alone: `POST /user/authenticators/{factor}/proof-options` with `action` (`remove`, `rename` or `replace`), `target`, and for a rename the new `name`, gives a challenge kept apart from sign in, step-up and enrollment ones. Its first answer uses it up, claimed in the rate limiter's store, so it can't be answered twice from a copy of the session or by two requests at once, whatever kind of key or factor answers it. A sign in or step-up, even with that key, doesn't count, so a copied session cookie can't make the change. For new recovery codes, or a factor a user has one of, the proof goes with the request that begins them, never the confirm. An established authenticator app counts too with the new `authenticator_changes.skip_with_totp` option, off by default, and `proof.authenticator` names which app when there's more than one. Recovery codes, an emailed code and the password never do. A change made this way freezes the account as any other would. See [Making a Change With an Established Key](docs/authenticators.md#making-a-change-with-an-established-key).
- The `authenticator_added` and `recovery_codes_generated` emails say what to do if it wasn't the user: remove the new method, sign out everywhere and change the password. With the new `authenticators_url` option, your page for sign-in methods, they link there, from `APP_URL`. `SecurityNotice` has an `ifNotYou()` method for that line.
- `AuthenticatorRemovalRefused` has a `reason`, `last_factor` or `frozen`, and so does the `authenticator_removal_refused` log entry. `EnrollmentRefused` and `enrollment_refused` can have the reason `frozen`.
- Linking an identity provider takes the password on the same terms as adding a second factor (`linkProvider()` takes `{ password }`), a new link freezes the account and an established one can't be unlinked while it's frozen, and a link is never the established second factor those checks look for, nor proves a change.
- `keyring:import` keeps when an imported authenticator app or passkey was first confirmed as when it was added, so it's established from the start. Imported recovery codes go by the app's confirmation too. With Fortify's `confirm` option off there's no date, so those accounts are frozen for 7 days after the import.
- The authenticator factory has an `established()` state, for a test's authenticator that the user has had a while.
- `@keyringjs/keyring` has a `FrozenChanges` type for the `frozen` in a refusal, with `skip`. `frozenChanges(error)` reads it, `proveWithKey(factor, { action, target, name? })` runs the ceremony for one change and returns its proof, and `removeAuthenticator()` and `renameAuthenticator()` take `proof`. `enroll()` sends a `proof` and a `password` with the beginning only.
- `json()` only sends the `X-XSRF-TOKEN` header to the page's own origin or the `baseUrl`, never to a full URL on another origin. It decides that from the URL as the browser parses it, so a URL that only looks like a path, such as `/\evil.test`, gets no token either. See the [upgrade guide](UPGRADE.md#the-xsrf-token-stays-on-your-origins).

## v0.3.0 - 2026-11-21

### Sessions and Devices

- A session keeps its handle when it moves to a new record: when "remember me" carries it on, when a risk response asks it to verify again, and with `rotate` on the `cookie` session driver. Each record names the one the session started on (`origin`), and the handle comes from that. Sessions that started before the upgrade keep the handles they had. Needs a new migration, see the [upgrade guide](UPGRADE.md).
- `Sessions::stillSignedIn($user, $handle)`, for code that knows a session by its handle to ask whether the user is still signed in on it. It applies `Keyring::allowSignInWhen()` and the session's timeouts, and it changes nothing.
- A conformance check that the session registry keeps `origin` when a session moves, so a missing migration or a custom driver that drops it is caught in your tests.
- The session registry says which records it revoked. `revoke()` returns the record it revoked, or `null` when it revoked nothing, and `revokeAll()` and `revokeDevice()` return the records they revoked instead of a count. Custom registry drivers need to return them too: see the [upgrade guide](UPGRADE.md#from-02-to-03). `Sessions::signOutEverywhere()`, `Sessions::revokeDevice()` and the `SessionsRevoked` event still give a count.
- The conformance suite checks that the configured registry returns the records it revoked.
- A `RegisteredSessionEnded` event for every registered session that ends, whoever ends it and wherever: signing out, the app's own `Auth::logout()` or `Auth::logoutCurrentDevice()` (announced as `logged_out` unless the app gives a reason of its own with `Sessions::because()`), signing out everywhere, ending a session or a device, the device and session limits, a deleted user, a risk response, a password change or reset, an email change or its undo, and the session middleware finding a session idle, expired, used twice or kept out. It names the session by its handle, with the handle under each previous app key too, and says why it ended (`Keyring\Enums\SessionEndReason`). It never carries the registry ID. On the `database` driver it goes out once the transaction it was revoked in commits, and not at all if that's rolled back. A listener that throws is reported and doesn't stop the sign-out. See [Hearing About Ended Sessions](docs/devices-and-sessions.md#hearing-about-ended-sessions).
- An `EveryoneSignedOut` event when `keyring:sign-out --all` or the registry's `revokeEveryone()` ends every user's sessions at once.
- Every registry driver, a custom one included, is wrapped in `AnnouncingSessionRegistry`, which dispatches those events from what the driver returns. `app(SessionRegistry::class)` returns the wrapper, and its `inner()` the driver. See the [upgrade guide](UPGRADE.md#the-session-registry-is-wrapped).
- A conformance check that signing out announces the session that ended, which fails when a `SessionRegistry` is bound in the container without the wrapper.
- A driver that fails after revoking some of a user's records throws a `PartialRevocation` with the ones it revoked, so they're still announced. The `cache` driver does this when the store fails part way through signing out everywhere, and keeps a revocation whose copy into the record fails. On the `cache` driver only, what a synchronous listener wrote on the user's connection is kept too, when Keyring's row lock is the outermost transaction: inside one of the app's own, the failure still rolls it back unless the app catches it. A database failure, deadlocks and lost connections included, always rolls it back. On the `database` driver with the registry on the user's connection, the failure rolls back the whole change, a sign in's new record included. With the registry on a `sessions.connection` of its own, it behaves as the `cache` driver does. On either driver, signing out everywhere still cycles the remember token, stops trusting devices and cancels a pending email change before the failure is thrown, signing a device out still cycles the remember token, and signing out everywhere else still gives this session a new ID.
- Registry IDs are marked `#[\SensitiveParameter]` on the contract, both drivers and `Sessions`, so they stay out of reported stack traces.
- `keyring:sweep`, which ends sessions that timed out with no request to end them and announces them as `idle` or `expired`, and announces again any ended session whose event was lost, so every ended session is announced at least once on the `database` driver. Turn it on with `sessions.sweep_every`, and Keyring schedules it before the prune, on one server and never overlapping. One run announces again, and ends, at most `sessions.sweep_limit` (1000) sessions each. A listener that throws is tried again five minutes later, then at doubling intervals for a day. Needs a new migration, see the [upgrade guide](UPGRADE.md#sweeping-ended-sessions).
- Once the new migration has run, `keyring:prune` keeps sessions a sweep still has to end or announce, whether or not one is scheduled. An expired session nobody ended stays up to a day longer before the prune removes it, and so does one the sweep ended for timing out, so its browser is still told why.
- `keyring:sign-out --all` marks the sessions it ends for its `EveryoneSignedOut`, so the sweep never announces them one by one, and counts them announced once the event has gone out. If it didn't, the sweep dispatches `EveryoneSignedOut` again, up to a day later, the latest of any lost ones, which settles the rest. Its `at` is a cut-off on sign-in time, never "end everything now".
- With the migration run, a record "remember me" moved a session to stays until it expires, so a used cookie still raises `RememberMeReused` after the sweep ended its session and the prune ran.
- `RememberMeReused` now also fires when the session a used cookie was carried on to has timed out since, so a sweep ending that session doesn't hide the reuse. The used record is revoked then, so the same cookie is reported once.
- A browser that comes back after its session was revoked once it had timed out, by the sweep or by signing out everywhere, is signed out as `idle` or `expired`, in `SessionEnded` and the security log, as it would be had nothing revoked it first. It used to say `revoked`. One the sweep ended keeps saying so until a day after its expiry. One signed out everywhere says so until the prune removes its record, a day at most.
- The database registry driver rethrows a failed query without its bindings, so record IDs, which are what "remember me" cookies hold, stay out of exception messages, logs and error trackers. `PartialRevocation` no longer repeats the failure's message.
- On the `cache` driver, revoking a record and moving it with "remember me" take turns under the owner's lock (on a store with locks), so a sign-out that lands mid-move is never lost without an event. A revocation that can't have the lock within five seconds goes ahead without it. On a `database` cache store, a failed cache query is rethrown without the cache keys it named, which hold record IDs.
- Signing out signs the browser out even when the session registry fails to revoke its record. The failure is still thrown, but the next request is a guest, where it used to be registered as a new session.
- `sessions.continue_as_guest` lists routes that also serve guests. A page visit to one whose session has ended is signed out and asked for again as a guest, rather than sent to log in, whatever the reason it ended. The `signed-out` status is flashed and no intended URL is saved. JSON requests still get a `401`.
- A sign-out your app does itself with `Auth::logout()` or `Auth::logoutCurrentDevice()`, on Keyring's guard in a request with a session, now ends the registered session too, with its "remember me" cookie and what the session proved. Before, the record stayed good until it timed out. On the `cookie` session driver, a copy of the session stayed signed in, and after `logoutCurrentDevice()`, so did a copy of its "remember me" cookies.

### Policies and Step-Up

- `StepUp::unlessMet()` to ask for step-up from a controller, for an integration that reads what to ask for from the request, such as an OpenID Connect provider with `acr_values` and `max_age`. It takes an `Assurance` level, a moment the user must have verified since, or both, and gives the same answer as the `keyring` and `keyring.fresh` middleware. Asking for nothing, or for a moment more than a few seconds in the future, throws.
- `StepUp::meets()` to ask the same thing without starting a step-up, for a request that mustn't show the user anything, such as one with `prompt=none`. It takes `unlessMet()`'s arguments and returns `true` where `unlessMet()` returns `null`, and leaves no confirm attempt or page to come back to in the session.
- `keyring:{level}` gives a guest Laravel's usual `AuthenticationException` even when the session still holds what the last user proved, as `keyring.fresh` already did. A session keeps that when the guard can no longer load its user, say because the account was deleted, and on a route without `auth`, the guest used to get through on it.
- The docs explain how to read what a session proved, for claims like `amr`, `acr`, and `auth_time`.
- `SessionAssurance::level()` and `countingToward()` take a timestamp, to count only what was proved since then with each level still on its own clock, so claims built for `max_age` don't report a level that lapsed.
- Users sent to enroll by `keyring.enrolled`, by step-up, or by the confirm page with nothing to confirm with now get the page they were going to back as `continue` on the `authenticator-added` status. Users held for a new password are redirected there by `password-updated`. Only top-level navigations and Inertia visits are remembered, and only on the app's own origin, for the same user, within an hour. Bind your own `Keyring\Login\Detours` and override `put()` to keep other pages out, such as `prompt=none` authorize requests.

### Logging and Emails

- A queued listener for `FactorChallenged` or `FactorVerified` now runs for an unsaved authenticator, such as the password's. It has nothing stored, so the job failed with a `ModelNotFoundException`. It's now queued as it is, without the user loaded with it, and a stored authenticator is still queued by its ID.
- An unsaved authenticator, such as the password's, now has its user's `authenticatable_type` and `authenticatable_id` set, so `owner()` finds the user, and `user()` looks them up again when they aren't loaded. Before, `owner()` ran a query Postgres refuses.
- `security_log.unlisted` lists entry types that `Keyring::activity()` leaves out, for entries a package writes about a user that aren't something the user did, such as a token issued to another app's server. They're still the user's entries: alerts, the log channel and a force delete treat them as before. `Keyring::unlistedActivityTypes()` gives the same types for an activity query of your own. Keyring's own types are never left out.

### Extending

- `StepUp` makes the decisions for the `keyring` and `keyring.fresh` middleware, and its constructor also takes a `DeviceManager`. What `keyring.fresh` asks for is `StepUp::freshRequirement()`, no longer the middleware's own `requirement()`. See the upgrade guide.

### Browser Package

- `@keyringjs/keyring` 0.1.1. `confirmEnrollment()` and `enroll()` include `continue` in their return type, for the page the user was going to before they were sent to enroll.

### Security

- A queued listener for `SessionResumed` or `RememberMeReused` no longer puts the session's registry ID on the queue. That ID is the value of the "remember me" cookie, so for `SessionResumed` it was a live one. Queued, the session's record now has a blank `id` and no `replacedBy` or `origin`, and both events always carry the session's `handle` to go by instead, the same one the sessions list shows. Listeners in the request see the record as before.
- Queueing a listener for an event that carries a sign in or step-up (`Authenticated`, `Confirmed`, `FactorChallenged`, `FactorVerified`, `VerificationRefused`) no longer puts the user's password hash and remember token on the queue. The attempt is queued as the plain data it keeps in the session and looks its user up again when asked. Jobs queued by 0.2 still restore, and drop the user they had cached.
- `AuthenticatorRemoved` now queues the user by ID like every other event, and the removed authenticator without its secret.

Restart your queue workers with the deploy. See the [upgrade guide](UPGRADE.md) for session events still on the queue, and for the old jobs in `failed_jobs` and Horizon.

## v0.1.0 - 2026-11-18

The first release.

### Signing In

- Sign in, sign out, registration, password resets and email verification, with your own actions and pages.
- Registration that doesn't reveal who has an account: the same answer for a free and a taken address, even when your action fails to create the user, with new users signing in once they've verified theirs, from the browser that followed the link, which gets a new session ID for it. `registration.reveal_taken` says when an address is taken instead.
- Factors behind one contract: password, authenticator apps, passkeys, security keys, email codes and recovery codes, plus your own. Many authenticators per user, with a default and "try another way".
- Passkeys and security keys from one WebAuthn driver: ES256 and EdDSA by default, RS256 when you ask for it, a challenge that is answered once and runs out on the server, and sign in with Laravel's `@laravel/passkeys` client. Like Laravel's passkeys package, the options name the relying party by its ID, so there's no name to set.
- `WebAuthn::securityKeys()->requireAttestation()` to only add hardware keys whose attestation chains to root certificates you list, and `allowOnly()` to limit them to certain models by AAGUID.
- Authenticator app codes that work once, with SHA-1, SHA-256 or SHA-512, and a window of one time step or none.
- Email codes as an extra step at sign in. They are opt-in and never count as a second factor.
- Recovery codes of 128 random bits, stored as keyed hashes, with a flag that says when a used set should be replaced.
- `Keyring::attempt()` to start a sign in from your own route, for social logins and the like.
- `Keyring::allowSignInWhen()` to keep banned or unapproved accounts out, however they try to sign in. The first request it refuses ends every session the account has.
- A verification pipeline you can add steps to, with the steps that enforce Keyring's guarantees protected from being removed by accident.

### Policies and Step-Up

- Policies built from assurance levels that follow NIST SP 800-63B-4: AAL2 needs a factor the user has, and AAL3 an attested key that can't leave its device. `ifEnrolled()` and `noDowngrade()` say how a policy treats users who can't meet it yet, or who have a passkey.
- `keyring.enrolled` to make everyone set up a second factor, which the installer adds when you pick one.
- Step-up middleware: `keyring:aal2` and `keyring.fresh:15m`, with a shared confirm flow. Changing how an account signs in takes the strongest proof the account can give, and a recovery code only counts there beside another factor.

### Sessions and Devices

- A registry of signed-in sessions that works on any session driver: a list of the user's sessions to end one by one, signing out everywhere else, a limit on sessions per account, and idle and absolute timeouts kept on the server.
- Assurance levels that lapse on NIST's clock, with `sessions.end_on_lapse` to end the session with its level.
- "Remember me" tied to the session it was ticked for: it carries that session on and can't outlast its timeouts, a revocation or a risk response. Its cookie works once and is replaced each time. A used one sent again ends the session for everyone holding it, with a `RememberMeReused` event and a `remember_me_reused` log entry.
- Devices: trusted devices, new-device emails with a "this wasn't me" link, and a limit on devices per account.
- `Secure`, `__Host-` prefixed cookies named for what they do (`known_device`, `remembered_session`).
- `keyring:sign-out` to end one user's sessions or everyone's.

### Account Changes

- Protected `email` and `password` attributes, which only change through Keyring's flows once it handles them.
- Email changes confirmed from both addresses and revertable from the old one, with the old address reserved while they can be undone.
- Password changes that take the current password and are only saved over the one that was checked, and resets that sign nobody in, end every session and leave second factors alone.
- Password rules that follow OWASP ASVS 5.0.0 and NIST SP 800-63B-4: 15 characters alone or 8 with a second factor, no composition rules, a bundled list of the most common passwords, your own context words, a breach check that can refuse what it couldn't check, Unicode normalised to NFC, and, with bcrypt, a password it would cut short or can't hash refused.
- `Keyring::requirePasswordChange()`, and a risk action of the same name, to hold a user until they choose a new password when theirs is known to someone else.
- Emailed links that only act on a button press, with the token or signature posted in the body, built from `APP_URL` and opened on pages that send no referrer.

### Rate Limits and Risk

- Rate limits per account, per typed username and per IP address, with locks that double, a count of their own for browsers the account has signed in from, a cap on failures in a row kept in the database, and `limits.lock_after` to keep an account locked until its password is reset.
- A timebox around every verification, registration and refused password reset, so a refusal takes the same time whatever the reason.
- Risk signals with an action for each level: a new device, a new country, impossible travel, a session turning up in another browser, repeated failed second factors, a sign in after several failures or after a long quiet period, a recently changed email address and a password found in a breach. A new app starts with the ones its features can feed, and a password found in a breach holds its user until they choose another.

### Logging and Emails

- A security log with a severity and a request ID on every entry, of sign ins, sessions "remember me" carried on, failures, lockouts, changes and what was refused, capped so a refused request can't fill it, and written whatever text an entry is about. Without the table it goes to your app's log.
- "Was this you?" alerts at the next sign in.
- Security emails about changes to how an account signs in and about suspicious attempts, sent from the start as far as your features go. Each is a notification you can swap for your own or turn off, and `SecurityNotice::toMailUsing()` writes them all from your own template.
- `support_contact`, so every notice can say who to contact.
- `Keyring\Events\*` for everything above, with Laravel's own auth events raised beside them.

### Tooling

- `keyring:install`, which asks which sign-in methods and features you want and publishes a config, a provider and your actions. Its defaults give the password alone, and every other sign-in method is in the provider, commented out, to turn on later. Also `keyring:import fortify`, and `keyring:prune`, scheduled daily.
- Security headers on Keyring's responses: `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy: same-origin-allow-popups` and a referrer policy.
- `Keyring::result()`, for a page to read what a form or Inertia response flashed for it, such as new recovery codes, which is kept encrypted in the session.
- Test helpers, a fake, factories, a virtual WebAuthn authenticator and a conformance suite that checks your setup still keeps Keyring's guarantees.
- `@keyringjs/keyring`, a browser package for WebAuthn, enrollment, sessions and the challenge page, with Vue and React bindings.
- Documentation of where Keyring stands on every requirement of OWASP ASVS 5.0.0 and NIST SP 800-63B-4 that bears on it, and of each place it deliberately does something else.
